## Interpretation

- Overall metrics aggregate multiple forecast horizons; they should not be presented as the accuracy of the full 168-hour forecast alone.
- Check the 168-hour metrics separately before describing a city model as reliable for the full seven days.
- A negative 168-hour R² means the model explains little test-set variance relative to the test-set mean, even when its MAE may still beat the persistence baseline.
- For deployment, show the city model as a seven-day forecast only with its horizon-specific validation context. For API fallback locations, show provider-returned AQI days and mark unavailable AQI days honestly.
- The next accuracy experiment should compare horizon-specific models, persistence/blended forecasts, and seasonal holdouts. Select changes using validation windows only; do not tune on the final test window.

## Current training design

The training pipeline uses chronological train/validation/test windows, 90-day validation and test windows, and a 168-hour purge. It does not use random splitting. Future weather values are served from Open-Meteo directly; local weather regressors are not required for the forecast UI.
